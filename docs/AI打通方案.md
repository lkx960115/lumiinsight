## 一、结论摘要

1. **现状：** AI 在系统里只承担两件事——逐条分类（ABSA）和措辞改写（摘要/建议/预警说明）。四处调用都被「不许编」的底线约束住（这是对的），但没有一处被允许「发现」新东西，因此 AI 的价值上限被压在规则引擎之上。
2. **机会：** 最值钱的一刀不是把打标做得更准，而是**把「一堆负向评论」变成「几类问题 + 为什么 + 证据」**。这是开放集语义任务，规则做不到，人读不完。
3. **建议：** 本轮打通 **S2 负向聚合归因**（P0），再接 S3 改进项化，S1 无词典槽点发现放后台并行。先做 S2 的理由：能用现有数据离线验证，不改前端也能看出「有没有发现人没发现的东西」。

## 二、现状诊断（代码事实）

| 触点 | 实际用法 | 代码位置 | 价值上限卡点 |
|---|---|---|---|
| ABSA 打标 | 每批 5 条；方面名必须落在词典或「其它」；失败回退词典规则；连续 2 批异常即停止 | `apps/ai-worker/app/absa.py` | 方面被词典锁死，未定义槽点全进「其它」，「其它」在报告中不可用 |
| 报告摘要/建议 | 只改写已给草稿；claims 必须带 evidenceIds；`ALLOWED_CODES` 仅 `summary` / `advice` | `apps/ai-worker/app/report_summary.py` | 只换措辞，不产新结论 |
| 问原评 | 只喂 snippets 原评，无工具、不能算数；无模型时走抽取式兜底 | `apps/ai-worker/app/ask.py` | 不能回答「占比/对比/趋势」类问题 |
| 预警说明 | 数字必须来自输入，一条一句 | `apps/ai-worker/app/alert.py` | 解释「变多」，不解释「为什么变多」 |

**判断：** 现有 AI 是「螺丝刀」——做得对，但不构成产品壁垒。壁垒应建在「规则做不了、人也做不完」的地方。

## 四、P0 方案：S2 负向聚合归因

### 4.1 目标与成功指标

| # | 目标 | 指标口径（估算值，待实测校准） |
|---|---|---|
| G1 | 报告能回答「这些差评到底是几类问题」 | 每份报告对 Top 3 负向方面各产出 3–5 类问题 |
| G2 | 每类问题可核对 | 每类带 ≥2 条真实原评 ID，且每条 ID 可在评论列表打开 |
| G3 | 归因质量达标 | 人工评审 ≥80% 类别被判「成立且有用」（样本：3 个项目 × 全部类别） |
| G4 | 不伤害现有体验 | 生成失败或无模型时，报告仍按现版本输出，不出现空节 |

### 4.2 用户与场景

- **用户：** 品牌方运营 / 产品经理；每月看一次报告，用来定「这个月先修什么」。
- **场景：** 打开项目报告 → 看到「亮度」负向 137 条 → 想看这 137 条分成哪几类、各多少条、典型原话是什么 → 决定是否立项。
- **现状成本：** 需人工逐条读完 137 条并自行归纳（按 15 秒/条估算约 34 分钟），且不同人归纳结果不一致。

### 4.3 方案对比

| 维度 | 方案 A：一次性大上下文归纳 | 方案 B：两阶段（向量聚簇 + 每簇命名）**推荐** | 方案 C：纯规则子词统计 |
|---|---|---|---|
| 做法 | 把某方面全部负向原文一次送模型，直接输出分类 | 先用现有向量/相似度聚簇，再对每簇做一次「命名 + 归因」调用 | 按词典子词/共现词分桶，输出统计 |
| 可扩展性 | 差：受上下文窗口限制，千条级即崩 | 好：成本与簇数相关，与总条数弱相关 | 好 |
| 归因质量 | 中（模型一次性压力大，易漏） | 好（每簇专注一件事） | 差（只能分组，不能命名与解释原因） |
| 实现成本 | 低 | 中（需聚类，但复用已有 embedding） | 低 |
| 降级路径 | 无 | 条数少时退化为 A；无模型/无向量时退化为 C | — |
| 风险 | 超长截断导致结论偏差 | 聚类质量差 → 簇无意义 | 输出无洞察，等于没做 |

**推荐方案 B，理由：** 它把「语义归并」交给向量（便宜、可重复），把「命名与解释」交给模型（贵、但只跑簇数那么多次）。这条分工让成本不随评论量线性上涨，也天然支持降级。

**演进路径：** 本期 B（按方面归因）→ 后续按「方面 × 月份」做归因漂移（谁的归因结构在变）→ 触发条件：归因采纳率稳定 ≥70% 后再投入。

### 4.4 功能需求

| 编号 | 需求 | 验收标准（Given / When / Then） |
|---|---|---|
| FR-01 | 对指定方面生成负向归因 | Given 项目已完成清洗分析且该方面负向 ≥10 条，When 生成报告，Then 报告出现「归因」节，含 3–5 类问题（条数降序） |
| FR-02 | 每类必须带证据 | Given 任一类问题，When 查看，Then 展示 ≥2 条原评（平台/时间/原文），点击可打开原评 |
| FR-03 | 无证据不得输出类别 | Given 模型返回的类别找不到匹配原评，When 装配报告，Then 该类别被丢弃（与现有 evidenceIds 校验口径一致） |
| FR-04 | 样本不足时明确说明 | Given 该方面负向 <10 条，When 生成报告，Then 显示「负向样本不足，本期不做归因」，不编造类别 |
| FR-05 | 降级不劣化 | Given 未配模型或调用超时，When 生成报告，Then 归因节显示「已按关键词分组」的粗分组 + 原评，报告其余部分与现版本一致 |
| FR-06 | 可反馈 | Given 任一类问题，When 用户点击「有用 / 没用」，Then 落库（类别 ID、动作、时间），用于后续评测 |

### 4.5 数据与接口（改动落点）

| 层 | 落点 | 说明 |
|---|---|---|
| Worker | 新增 `POST /v1/jobs/attribute` | 入参：方面名、负向原评列表（含 id）、可选簇数量；出参：`items[{name, size, reason, evidenceIds}]` |
| Worker | 复用 `app/llm.py` 的 `chat_json` | 沿用现有超时/重试/用量记账，不新建调用通道 |
| Java | `modules/report/ReportComposer` | 报告装配时调 Worker，失败即跳过该节 |
| Java | `modules/report/ReportComposer` 报告结构 | 现有 8 节（summary / volume / sentiment / aspects / quotes / compete / advice / ask），新增第 9 节 `code=attribution`；**注意**`report_summary.py` 的 `ALLOWED_CODES` 仅 `summary`/`advice`，归因节默认不会被模型改写——若希望它也走顾问口吻，须同步放开白名单，否则文案保持规则稿 |
| 数据 | 复用 `review_aspect`、`evidence` | 不新增主表；归因结果随 `report` 快照落库（与现有报告一致） |
| 前端 | 报告页新增「归因」节 | 遵循 `docs/ai/PRODUCT_UI.md`：列表 + 展开原评 + 空状态 + 失败提示 |

### 4.6 关键约束与已知坑

1. **章节白名单**：`ALLOWED_CODES` 不放开的章节不会被模型改写（保持规则稿文案），若误以为「加进报告就自动变好看」会白等——文案是否走模型要显式决定。
2. **报告节顺序**：`ReportComposer` 按固定顺序拼装且过滤空节，归因节要插在「方面痛点与卖点」之后、「改进建议」之前，否则读者先看到建议、后看到依据。
3. **证据校验**：归因的证据 ID 必须落在本次调用的 allowed 集合内（现有 `filter_ids` 逻辑），否则会出现「引用别项目原评」。
4. **成本**：一次归因 ≈ 簇数（3–5）次调用，不随评论总数线性增长；需在用量页可见。
5. **确定性**：同名方面两次生成的类别名可能不同 → 类别名不做唯一约束，仅存快照。
6. **中文与脱敏**：原评已在清洗阶段脱敏，送模型前不得回填明文（沿用现规则）。

### 4.7 风险登记

| 编号 | 风险 | 概率×影响 | 等级 | 应对 |
|---|---|---|---|---|
| RK-01 | 聚类质量差，簇内混杂 → 类别名空泛（如「质量问题」） | 4×4=16 | 高 | 先按方面内聚；簇数上限 5；类别名必须含具体触发描述，评审不通过则退化为 A |
| RK-02 | 归因看起来像事实，用户直接拿去汇报 | 3×5=15 | 高 | 每类强制带原评；页面固定提示「归因为模型归纳，需核对原评」 |
| RK-03 | 调模型不稳定导致报告生成变慢/失败 | 3×3=9 | 中 | 归因失败不阻塞报告主流程（与现有摘要一致的降级策略） |
| RK-04 | 成本超预期 | 2×3=6 | 低 | 用量页可见；按项目维度设月调用上限 |
| RK-05 | 无标注集，无法证明有效 | 4×3=12 | 中 | 本期同步建 20–30 份报告的人工标注集（见第六节） |

### 4.8 验收与下一步

| # | 动作 | 依赖分级 | 说明 |
|---|---|---|---|
| 1 | 确认归因节在报告中的位置与文案口吻 | 阻塞 | 决定前端信息层级 |
| 2 | 建标注集：3 个项目、每个 Top3 方面、人工写出「应有几类」 | 并行 | 无此集则 G3 无法验收 |

## 五、S1 / S3 简述（P0 其余两项）

**S3 评论 → 改进项**
- 输入 S2 的类别结果 + 条数占比 + 平台分布；输出：问题描述、影响面、建议动作、优先级、证据链。
- 形态待定：报告内洞察段 **或** 可导出工单条目（决定是否需要导出/对接层）。
- 验收：一份报告出 3–5 条，业务方判断「可直接进排期」≥2 条。

**S1 无词典槽点发现（词典飞轮）**
- 对「其它」及未命中评论做开放集方面抽取 → 聚类 → 候选新方面 + 建议关键词 → 后台待审。
- 只做提案，**不自动入词典**；采纳后下轮 ABSA 命中数应上升。
- 验收：候选方面人工采纳率 ≥30%。

## 七、顺手降本：ABSA 改级联

现状每条评论都进模型（`absa.py` 批 5 条）。改为：**规则高置信直接过，只把「词典未命中 / 正负词冲突 / 归到其它」送模型**。
- 预期调用量降 60–70%（估算，需用现有样例实测）；
- 用户体验不变（规则本就在兜底）；
- 省下的预算正好覆盖 S2/S3 的增量调用。

---

## 八、本期明确不做

- 不做端到端微调/自训练模型（继续走「可配置模型 + 规则约束」）；
- 不做多模态（图片评论、详情页截图）；
- 不做四平台真实拉取（沿用现有空适配器）；
- 不自动改写方面词典（只做候选提案）；
- 不做公网开放 API。

## 十、离线验证记录（W1 前半，2026-10-30）

**脚本：** `eval/offline_attribution_probe.py`（只读样例、不调模型、不改业务代码，可重复执行）
**输出：** `eval/归因离线验证-2026-10-30.md`

### 10.1 做了什么

用真实规则引擎（`absa.py` 的 `rule_aspects`）从 141 条样例里筛出负向评论，按方面做字符 bigram 相似度聚类，看簇是否可读。

### 10.2 结果

| 判据 | 结果 | 判断 |
|---|---|---|
| 负向样本量 | 色温 15 / 物流 13 / 价格 13 / 遥控 13 / 智能联动 13 | 通过 |
| 表述多样性 | 独特表述 4 / 2 / 2 / 2 / 2，独特率 15–27% | **不通过** |
| 簇可读性 | 可读，但大簇实为「同一句模板 × 不同日期」 | 不构成证据 |

**结论：现有黄金集能测 ABSA 判对错，但测不了归因质量——因为样例是模板生成的重复数据。**

### 10.3 由此新增的需求与风险

| 编号 | 新增内容 | 说明 |
|---|---|---|
| FR-07 | 归因前先按原文去重并统计独特表述数；独特表述 <10 条的方面显示「表述单一，本期不做归因」 | 防止线上产出「13 条同一句话」的空聚类 |
| FR-08 | 归因聚类输入必须是**去重后的独特表述**，条数按原始条数回显 | 去重后聚类，展示时还原真实影响面 |
| RK-06 | 评测集多样性不足导致归因质量无法验证 | 概率 5 × 影响 4 = 20（高）；应对：先建多样性评测集（3 方面 × 30 条不同表述，虚构数据需标注），通过后再开发 |

### 10.4 下一步

建议先建「多样性归因评测集」（选项 2，成本最低、可立即做），用它验证聚类能否分开人写出来的不同槽点；通过后再进入 W1 后半。

## 十一、第二轮验证：多样性评测集（2026-10-30）

**评测集：** `eval/fixtures/attribution-diversity.csv`（90 条，虚构，3 方面 × 4 子槽点，独特率 100%）
**报告：** `eval/归因离线验证-第二轮-2026-10-30.md`

### 11.1 聚簇结论：字面相似度不可用

售后 16 条 → 15 簇（碎片度 3.8）、安装 14 条 → 8 簇（碎片度 2.0）。纯度虽 100%，但等于一条一簇。
**语义归并必须靠 embedding：** 依赖分级由「可绕过」上调为 **阻塞**，未配 embedding 时归因不启用（降级到字面聚类比不做更糟）。

### 11.2 发现的三个规则/词典缺陷（归因上线前必须修）

| 编号 | 问题 | 位置 | 性质 |
|---|---|---|---|
| D1 | `NEGATORS` 不含「不」，`POS_WORDS` 含「够亮」→「不够亮」被判正向 | `absa.py:84`、`126-127` | Bug，影响全站情感统计 |
| D2 | 亮度词典只认「太暗/暗了」，漏「偏暗/发暗/越来越暗/照不亮」 | `V4/V11/V12` 关键词 | 词典覆盖缺口 |
| D3 | 「刺眼」归属频闪，导致亮度-刺眼问题被吸走 | `V11` | 归属争议，需产品拍板 |

### 11.3 新增需求与风险

| 编号 | 内容 |
|---|---|
| FR-09 | 单簇条数 <总数 5% 视为碎片，必须合并或丢弃；簇数 >8 且碎片度 >3 判定归因不可用，改为只给原评列表 |
| FR-10 | 归因上线前先修 D1 与 D2；输入池错误时，归因质量无从谈起 |
| RK-07 | 禁止以字面聚类作为降级路径（概率 4 × 影响 4 = 16，高） |
