## 1. 产品定位与非目标

**定位：** 面向灯具品牌的评论洞察平台：导入评论 → 去水 → 方面级情感（ABSA）→ 结论可溯源 → 自动报告。

**MVP 做：** 本地账号；项目；Excel 导入；清洗分析；单品报告与点选溯源；后台（用户、词典、**多模型配置**、审计）。

**MVP 不做：** 交易客服；未授权采集；四平台真爬取；智能问答；预警；多模态；Linux/K8s 生产部署。

## 3. 逻辑架构

```text
浏览器 (Vue3)
   │  JWT
   ▼
Spring Boot (apps/server)
   │  项目 / 导入 / 权限 / 任务编排 / 报告装配 / 模型配置
   ├─ MySQL 8          主数据、任务状态、模型配置密文
   ├─ Redis            会话、限流、队列辅助
   ├─ MinIO            导入文件、导出文件
   ├─ Qdrant           评论向量（W3）
   └─ HTTP
        ▼
FastAPI (apps/ai-worker)
        └─ 按「模型配置」调用各 LLM / Embedding（OpenAI 兼容为主）
```

**原则：** 浏览器不直连 Worker、不直连 Qdrant。Worker 不拥有账号权限模型。

## 4. 技术栈（锁定）

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | Vue 3 + Vite + TypeScript + **Element Plus** | 同一工程 |
| 路由 | `/app/*` 工作台；`/admin/*` 管理端；`/login` | 同一登录态，菜单按角色 |
| 后端 | JDK 17 + Spring Boot 3 + MyBatis-Plus | REST |
| 鉴权 | JWT + 本地用户密码（BCrypt） | 不做 SSO |
| AI Worker | Python 3.11 + FastAPI | 重 NLP / 批处理 |
| 主库 | MySQL 8 | |
| 缓存 | Redis | |
| 向量 | Qdrant（Docker） | W3；可降级 MySQL 检索 |
| 对象存储 | MinIO（Docker） | 本地；以后可换 OSS |
| 图表 | ECharts | |
| 导出 MVP | Excel + Markdown | PDF/PPT 三周后 |
| LLM | **后台多提供方配置**（见第 8 章） | 默认预置智谱 GLM（OpenAI 兼容） |
| Embedding | 可与聊天模型分配置 | 可先用提供方 embedding 接口 |
| 本地运行 | docker-compose + IDE 启应用 | 先本机，后 Linux |

禁止无确认改用 React、替换为单体 Python Web、上 K8s、引入未评审的微服务拆分。

### 4.1 选型原则

1. **先本机、三周能交：** Docker 起依赖，IDE 起三个应用；不上 K8s、服务网格。
2. **权限与数据在 Java：** 登录、项目范围、审计、任务状态只在 `apps/server`；浏览器和 Worker 都不直连向量库、对象存储。
3. **模型可换、不写死厂商：** 后台多提供方 + OpenAI 兼容协议；禁止把智谱或任何一家做成唯一调用路径。
4. **能降级：** 向量写不上就按方面关键词找回；对象存储以后可换 OSS；图表可先统计后装饰。
5. **公开仓干净：** Key 不进 Git；采集 MVP 只导入，四平台适配器保持空实现。

### 4.2 选型分析（为何选、为何不选）

| 决策 | 选择 | 对比过 | 为什么这样 | 三周内不做什么 |
|------|------|--------|------------|----------------|
| 前端 | Vue 3 + Vite + TS + Element Plus | React / Ant Design Vue | 后台表单、表格、权限指令交付快；与现有产品界面标准一致 | 不上 SSR、不拆微前端 |
| 图表 | ECharts | Chart.js / 纯 CSS | 情感饼图、方面堆叠条是工作台主路径，ECharts 现成 | 不做大屏、不做 GIS |
| 业务后端 | JDK 17 + Spring Boot 3 + MyBatis-Plus | 单体 FastAPI / Node | RBAC、事务、异步任务、Flyway 改表是主路径；团队 Java 交付稳 | 不拆微服务、不升 Boot 4 |
| 鉴权 | 本地用户 + JWT + BCrypt | SSO / OAuth | 参赛/内网先跑通；账号在本库即可审计 | 不做公司统一登录 |
| AI 计算 | Python 3.11 + FastAPI Worker | 全放 Java NLP | 清洗、ABSA、embedding 批处理更适合 Python；Java 只编排和落库 | Worker 不做登录、不对外网关 |
| 主数据 | MySQL 8 | PostgreSQL | 账号、项目、评论、证据、任务都要事务和报表查询；本机已有独立 8 实例（不复用 5.7） | 不用分库分表 |
| 缓存/辅助 | Redis | 只用内存 / 只用 MySQL | 会话、限流、任务辅助；与主库解耦 | 不上消息集群 |
| 向量 | **Qdrant** | Milvus、pgvector、Elasticsearch | 见 4.3 | 工作台按方面找回仍可只走 MySQL |
| 文件 | MinIO | 本地磁盘 / 云 OSS | 导入 Excel、失败行报告要对象路径；API 与 S3 接近，以后换 OSS 少改 | 不上 CDN |
| LLM 协议 | `openai_compat` 多提供方 | 各家官方 SDK 写死 | 换 Key、换智谱/DeepSeek/自定义地址不改业务代码 | 第一期不做 Anthropic 专用协议 |
| 运行形态 | compose + 本机三进程 | 全容器化应用 / K8s | 前端、Java、Worker 要热改；依赖用容器即可 | Linux 生产部署后置 |
| 导出 | Excel + Markdown | 先做 PDF/PPT | 先保证结论带证据能打开；版式后补 | 三周内不锁 Word 模板 |

前后端拆开而不是「Java 里嵌页面」：工作台和管理端同一 Vue 工程、两套路由，权限码三处同名（菜单 SQL、后端注解、`v-permission`）。NLP 不进浏览器，避免 Key 和词典规则泄漏到前端。

### 4.3 向量库为什么用 Qdrant

灯鉴要存的是「一条有效评论一个向量」，payload 只要项目 ID 和方面名，给后续语义找回原评用。当前工作台点方面条仍读 MySQL 证据/方面表；Qdrant 是写入与后续语义检索的位置，**不是列表主库**。

| 方案 | 适合 | 不选用的原因（对本仓） |
|------|------|------------------------|
| **Qdrant** | 独立向量服务、HTTP 即可、Docker 一条拉起、控制台能看集合 | **入选。** 集合名 `lumi_reviews`，Java 写入，浏览器不直连。 |
| Milvus | 亿级、运维重 | 本机 compose + 三周体量过重，依赖多 |
| pgvector | 数据已在 Postgres | 主库是 MySQL，为向量再换主库或双库不划算 |
| ES kNN | 已有搜索集群 | 本仓没有 ES；为评论检索再引入一套搜索过重 |
| 只用 MySQL | 方面名、关键词 | **已作为降级：** 未配 embedding、Qdrant 挂了、写入失败时，仍按方面拉回原评 |

约束：

- 「向量检索」用途必须配 **embedding 模型**（如 `text-embedding-3-small`）。聊天模型不能当向量模型，否则集合为空。
- 维度以第一次成功写入为准；换模型导致维度变化时需重建集合（三周内按重跑分析处理，不做在线迁维）。
- 删除项目/评论时，向量与证据应一并失效（见依赖图谱）；未做级联前不要把 Qdrant 当唯一真相。

## 8. LLM：后台配置、支持多种（已锁定）

**回答第 1 点：是。** 模型不写死在代码里。后台「模型配置」维护提供方与路由；Java 编排按 **用途（route）** 取配置，再交给 Worker 或 Java HTTP 客户端调用。

### 8.1 提供方（LlmProvider）

| 字段 | 说明 |
|------|------|
| name | 展示名，如「智谱」「DeepSeek」「自定义」 |
| protocol | 第一期只支持 `openai_compat` |
| baseUrl | 如智谱 `https://open.bigmodel.cn/api/paas/v4` |
| apiKeyCipher | Key **加密存储**，列表只显示后四位 |
| extraHeaders | 可选 JSON |
| enabled | 启停 |
| timeoutMs / maxRetry | 超时与重试 |

预置提供方（可改可关，不是代码常量）：智谱 GLM、DeepSeek、OpenAI、通义兼容端点、**自定义 Base URL**。

### 8.2 模型（LlmModel）

挂在提供方下：`modelCode`（厂商模型 ID）、上下文长度、是否支持 JSON Mode、输入/输出单价（用于成本页）、启用状态。

### 8.3 用途路由（LlmRoute）

同一系统可同时配多套模型：

| 用途 code | 典型 |
|-----------|------|
| `absa` | 方面抽取与情感 |
| `sentiment` | 整句情感（可与 ABSA 共用） |
| `report_summary` | 报告摘要（须基于统计+证据，禁止空手编造） |
| `embedding` | 向量 |
| `spam_classify` | 去水辅助（可先规则，模型可选） |

每条路由：主模型 + **备用模型**（主失败/超时则切备用）。未配置时才读本机环境变量兜底（`.env.example`），生产应以库内配置为准。

### 8.4 调用与安全

- 后台「测试连通」只发最短请求，结果写日志。  
- 日限额、token 记账到 `llm_usage`。  
- Key 不进 Git、不进前端接口明文、不进公开 README。  
- 换 Key、轮换提供方 **不改业务代码**。

### 8.5 与 Harness 的关系

模型再强，报告也不允许跳过证据校验。多模型只解决「用哪家脑子」；「必须引用原评」是 L6 约束，与提供方无关。

## 9. 流水线与 Harness

状态：`PENDING → IMPORTING → CLEANING → ANALYZING → INDEXING → REPORTING → READY / FAILED`。

| Harness 层 | MVP（三周） |
|------------|-------------|
| L1 信息边界 | 项目范围 + 方面词典 + 仅已入库评论 |
| L2 工具 | 统计、检索证据、填模板；无通用浏览器爬取工具 |
| L3 编排 | 上表状态机，LLM 不改顺序 |
| L4 状态 | 全落库，不靠聊天记忆 |
| L5 评估 | 三周内只做引用覆盖校验；黄金集 W2 末占位 |
| L6 恢复 | 重试、备用模型、无证据不出结论 |

开发侧：`AGENTS.md` + D1–D6 + 改前确认，对标 MCP 仓方法论，不引入额外 Harness 商业产品。

## 10. 本地运行（代码周生效）

1. 复制 `.env.example` → `.env`（切勿提交）。  
2. `docker compose up -d`。  
3. 启动 `apps/server`、`apps/ai-worker`、`apps/web`。  
4. 浏览器打开前端，用本地账号登录。  
5. 管理端配置至少一个 LLM 提供方后再跑分析。  

Linux 部署不在三周范围，届时仍以 compose 为默认形态。

## 11. 接口风格（约定）

- REST，JSON，统一包装 `{ code, message, data }`。  
- 写操作记审计日志。  
- 导入、分析、报告生成为异步任务，查询任务进度，禁止同步卡死 HTTP。
